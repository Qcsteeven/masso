# МАССО — мультиагентная система ситуативного обучения

Опытный образец (первая очередь) по ТЗ и ТП редакции 2 (`docs/rev2/`). Обучающийся получает индивидуальный вариант учебного инцидента — DevOps-сервер с поломкой в изолированном контейнере или документный кейс (юридический, аудиторский), решает его в браузере, получает подсказки, динамический инцидент и автоматическую оценку; профиль компетенций обновляется, преподаватель видит цифровой след и корректирует оценку.

Состав: Frontend (React SPA за nginx) → Backend/API (FastAPI, агенты на LangGraph, LLM Gateway, Sandbox Manager, фоновый worker) → PostgreSQL 18 + pgvector; учебные среды — контейнеры `masso/webstack`, которые backend создаёт через Docker Engine хоста. Подробности — `docs/02-mvp-spec.md`, результаты испытаний — `docs/test-report.md`.

## 1. Развёртывание на чистой Linux-ВМ

Пошагово для своего компьютера (Windows + WSL2 или Linux), с разбором типичных ошибок, — [docs/LOCAL-RUN.md](docs/LOCAL-RUN.md).

**Требования к ВМ.** Ubuntu 24.04 / Debian 12 (x86_64), Docker Engine 27+ с плагином Compose v2+, `git`, `make`. Ресурсы: для демонстрации — 4 vCPU, 8 ГБ RAM, 20 ГБ диска; для 50 одновременных сессий — 16 vCPU, 64 ГБ (ТЗ 4.10). Порт 80 (или `HTTP_PORT`) открыт для пользователей. ВМ должна быть выделенной: backend управляет контейнерами хоста через `/var/run/docker.sock` (ТЗ 4.11); внутрь учебных сред сокет не пробрасывается. Квота диска учебной среды контролируется раз в минуту, поэтому каталог данных Docker (`data-root` в `/etc/docker/daemon.json`) лучше вынести на отдельный раздел, чтобы переполнение не затронуло ОС, а резервные копии БД хранить вне этого раздела.

```bash
# 0. Docker (если не установлен) — официальный скрипт, затем перелогиниться
curl -fsSL https://get.docker.com | sudo sh && sudo usermod -aG docker $USER

# 1. Код и настройки
git clone https://github.com/Qcsteeven/masso.git && cd masso
cp .env.example .env
#    обязательно поменять в .env: POSTGRES_PASSWORD (и его же в DATABASE_URL), JWT_SECRET (≥ 32 символа);
#    LLM: заполнить LLM_EXTERNAL_* или оставить пустым — система работает в шаблонном режиме

# 2. Система: сборка и запуск (миграции БД применяются при старте backend)
make up                 # http://<адрес ВМ>/ ; другой порт: HTTP_PORT=8080 make up
make seed               # роли, демо-пользователи, граф компетенций, 3 шаблона сценариев (идемпотентно)
make sandbox-image      # образ учебного сервера masso/webstack (≈ 1–3 мин)

# 3. Проверка
curl -s localhost/api/health     # "db":"ok", "worker": {...}
```

Если `make seed` сразу после `make up` пишет об отсутствии таблиц — backend ещё применяет миграции, повторите через 10 с.

**Локальная LLM (необязательно).** `docker compose --profile llm up -d ollama`, затем `docker compose exec ollama ollama pull <модель>` и в `.env`: `LLM_LOCAL_CHAT_MODEL=<модель>`, `LLM_GENERATION_MODE=local`, `make up`. Проверка провайдеров: `cd backend && uv run python ../scripts/llm_smoke.py external|local`.

**Эксплуатация.**

| Задача | Команда |
|---|---|
| Журналы | `make logs` |
| Остановить / запустить | `make down` / `make up` |
| Резервная копия БД (ТЗ 4.8, ежедневно, хранить ≥ 30 дней) | `docker compose exec -T db pg_dump -U masso -Fc masso > backup/masso-$(date +%F).dump` — в cron: `15 2 * * * cd /opt/masso && docker compose exec -T db pg_dump -U masso -Fc masso > backup/masso-$(date +\%F).dump && find backup -mtime +30 -delete` |
| Восстановление | `docker compose exec -T db pg_restore -U masso -d masso --clean < backup/masso-ДАТА.dump` |
| Метрики Prometheus | `GET /metrics` на backend (из внутренней сети) |
| Нагрузочный прогон | `cd backend && uv run python ../scripts/loadtest.py -n 20 --base http://localhost` (для N > 20 поднять `SANDBOX_MAX_SESSIONS`) |

Основные параметры `.env`: `SANDBOX_MAX_SESSIONS` (лимит одновременных учебных сред, по умолчанию 20), `SANDBOX_IDLE_PAUSE_MIN` / `SANDBOX_EXPIRE_HOURS` (пауза и завершение по бездействию), `INSTANCE_ID` (метка установки, если на одном Docker несколько стендов), `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` (пул соединений; увеличить вместе с числом сессий).

## 3. Сценарий демонстрации на защите (5 минут)

Подготовка до начала (не на время): `make up && make seed && make sandbox-image`; войти преподавателем и назначить группе «Восстановление веб-сервиса» (Назначения → шаблон → группа ИСИб-23-1); открыть два окна браузера (обычное и инкогнито). Если сеть на защите ненадёжна — администратор заранее включает режим `template` (LLM и песочницы → режим генерации).

| Время | Кто | Действия и что сказать |
|---|---|---|
| 0:00–0:30 | — | Экран входа. «Пять ролей ТЗ, JWT с ротацией refresh-токенов; агенты ProfileAgent, ScenarioAgent, AssessmentAgent». |
| 0:30–1:00 | Обучающийся `demonov.la` | Панель: назначения, рекомендации по дефицитам навыков. Нажать «Начать» у «Восстановление веб-сервиса». Пока идёт генерация (≈ 20 с): «ScenarioAgent сгенерировал вариант и проверил его прогоном в отдельном контейнере: сбой ломает проверки, эталонное исправление их восстанавливает — неразрешимый вариант студент не получит». |
| 1:00–2:30 | Обучающийся | Рабочая область: легенда, таймер, терминал. Ввести: `supervisorctl status` (store-api в ошибке) → `tail -n 5 /srv/log/store-api.log` (ошибка аутентификации БД) → `diff /srv/app/.env.example /srv/app/.env` → исправить: `sed -i 's/^DB_USER=.*/DB_USER=store/; s/^DB_PASSWORD=.*/DB_PASSWORD=Sh0p-2026-store/' /srv/app/.env && supervisorctl restart store-api` → `curl -s localhost:8080/health`. Попросить подсказку: «показывает область проблемы без команды, −10 % к баллу, не больше трёх». Ввести `sudo -i`: «попытка заблокирована и попала в события безопасности». |
| 2:30–3:15 | Обучающийся | Через 2–5 минут после старта приходит инцидент «502 Bad Gateway» (журнал справа). Исправить: `sed -i 's/127.0.0.1:8001/127.0.0.1:8000/' /srv/nginx/store.conf && supervisorctl restart nginx`. Если инцидент ещё не пришёл — показать, что проверки ждут его («инцидент не наступил» засчитывается), и отправить. «Завершить и отправить» → протокол: балл с расчётом (с подсказкой и `sudo` — 80 = 100 × 0,9 − 10), проверки с весами, изменения навыков. «Контейнер удалён в течение 30 с». |
| 3:15–4:15 | Преподаватель `teacher` | Панель группы → период → сессия обучающегося → цифровой след: команды, подсказка, инцидент, событие безопасности. Скорректировать оценку с причиной: «причина обязательна, запись в журнал аудита». |
| 4:15–5:00 | Администратор `admin` / `ops` | LLM и песочницы: переключить режим на `template` с причиной — «активные сессии не прерываются, у преподавателя баннер». Состояние системы (`ops`): учебные среды, события безопасности с `sudo` из демо. Финал: «испытания ТЗ 6.3 — `docs/test-report.md`, нагрузка — 50 сессий без ошибок». |

Запасной вариант без Docker-песочницы: назначить и пройти «Аудиторскую сверку счетов» (документный тренажёр) — тот же путь: генерация → инцидент → подсказка → отправка → протокол.

## Демо в браузере (GitHub Pages)

https://qcsteeven.github.io/masso/demo/ — тот же интерфейс без сервера: backend, база и учебный сервер имитируются в браузере (`frontend/src/demo/`), данные экранов записаны с работающего стенда (обезличенные пользователи), вместо LLM — утверждённые варианты. Вход — кнопками ролей на экране входа (пароль `masso-demo`). Можно пройти DevOps-сценарий в терминале с инцидентом через 75 с, документные кейсы, посмотреть сессию у преподавателя. Локально: `cd frontend && pnpm build:demo` → `site/demo/`. Публикация — workflow `.github/workflows/pages.yml` при пуше в `main` (один раз включить: Settings → Pages → Source: GitHub Actions).

## 4. Разработка

|---|---|
| `make dev-db` | PostgreSQL + pgvector для разработки и тестов на порту 5433 |
| `make dev-back` / `make dev-front` | backend с перезагрузкой (порт 8000) / Vite dev server |
| `make check` | ruff, mypy strict, oxlint, tsc, unit- и API-тесты backend, vitest — перед каждым коммитом |
| `make test-integration` | тесты с реальным Docker и образом песочницы |
| `make e2e` | Playwright по поднятому стенду (`E2E_BASE_URL`, по умолчанию `http://localhost:8080`) |
